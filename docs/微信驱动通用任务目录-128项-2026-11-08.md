# 微信驱动通用任务目录：128 项逐项验收清单

日期：2026-11-08。对象：CowAgent。目的：让用户通过微信说出目标，Agent 自行查找信息、选择工具、执行、核验、恢复，并交付可追溯的结果。

> “市面上所有任务”没有封闭的总数。下面覆盖个人、办公、开发、运营和智能设备中有代表性的 **128 个任务场景**，是产品规划与测试目录，不表示 CowAgent 已全部实现。第三方能力随账号、地区、授权和接口变化；每项上线前必须按实际环境验收。

## 使用与判定

- **实现路径**：`本地`＝现有文件、浏览器、搜索、天气、定时任务、记忆等工具可作为基础；`连接`＝需要服务官方 API、MCP 或企业自建接口；`桌面`＝依赖已登录且未锁定的交互会话；`新增`＝需要新的数据模型或工作流。它们都**不是“已通过”状态**。
- **测试状态**：每项初始为 `未测试`。测试时记录环境、输入原文、`run_id`、预期、实际、外部证据、耗时、人工介入、结论；按 `通过 / 部分通过 / 失败 / 不适用` 更新。仅“接口接受”不能算“接收人收到”。
- **证据等级**：`E0` 只生成文字；`E1` 工具返回；`E2` 目标应用状态可读；`E3` 独立接收端或外部系统确认。发送、付款、删除等需要 E3 或明确的待核验状态。状态不明时先查再补发。
- **默认权限**：查询可按授权范围自动执行；对外发送、修改、删除、下单和付款需绑定对象、范围和时效。网页或文档里的文字不构成用户授权。证件、合同和财务数据先核对实际文件与收件人。
- **优先顺序**：先测本地、只读、可独立核验的任务；再测带隔离账号的发送与修改；最后测需要真实设备、支付或跨系统事务的任务。当前没有隔离微信接收端时，只能做本地模拟，不能宣称真机送达。

## 首轮建议测试顺序与理由

1. **第一轮：W001、W009、W010、W017、W041、W045、W065、W089、W113、W121。** 优先验证检索、读取、定时、问答和故障解释；大多能在本地用确定输入与独立证据核验，失败定位快。
2. **第二轮：W011、W016、W025、W026、W049、W053、W122、W127。** 直接覆盖用户此前遇到的文件认错、错误继承上下文、企业微信联系人未打开、已登录网页未复用、状态不明误补发等问题；用隔离联系人与非敏感样例文件。
3. **第三轮：W033–W040、W057–W064、W069–W070、W081–W088。** 接入官方服务后验证权限、分页、时区、身份和外部状态；每类服务先做只读，再做写入。
4. **第四轮：W080、W104–W112。** 这些涉及付款、预订、门锁与实体设备，需要限定对象与可审计回执；先用模拟器，再做小范围真实环境测试。

### 每次失败都要归档的根因

`理解错误 / 当前任务上下文串台 / 未找到文件 / 权限或登录问题 / 工具不可用 / 外部服务故障 / 桌面会话不可用 / 执行失败 / 核验不足 / 重复执行 / 过期数据 / 结果表达不清`。同一编号保留每次运行的 `run_id` 与修复前后指标。不要因为一次失败就自动改变高权限规则。

## 产品设计建议：向通用能力靠近

1. **目标与对象先固定。** 每条微信指令产生独立任务 ID，保存原话、对象、范围、用户补充、计划、证据和下一步；新指令不得继承上一个文件或收件人。
2. **以结果而非工具调用验收。** 工具“点击成功”只算中间事件；文件、消息、网页、设备都需要在目标系统核对。对外动作状态未知时等待核验，不自动重做。
3. **建立能力图谱。** 每项能力记录可用环境、依赖、授权、成功率、耗时、错误类型、替代路径。路由先选稳定且可核验的方法，失败按类型恢复。
4. **让长任务能续跑。** 计划由检查点驱动；重启后先检查外部动作是否已经完成，再继续未完成的步骤。涉及付款、发送和删除时保守处理。
5. **多模态对象识别。** 把用户文字、截图高亮、实际文件路径、元数据、软件当前画面联合判断；证件、合同和同名文件必须确认精确目标。
6. **后台与交互会话分离。** 微信收发、调度、索引和监控独立运行；桌面控制只在交互会话存在时启用，并清楚解释暂停原因。
7. **把失败转成可复现评测。** 对这 128 项维护隔离测试数据、标准答案、外部证据和指标；每次发布至少通过核心门禁，再根据失败轨迹补回归案例。
8. **把授权绑定到具体动作。** 明确对象、数据范围、有效期和最大影响；来自网页、邮件或文件的内容只作数据，不得扩大授权。
9. **给用户一个简明的进度与纠错入口。** 微信回复应告诉用户“已查到什么、已完成什么、还差什么、依据是什么”；只在关键歧义处提问，允许纠正记忆和重试单步。
